# 测试规范

## 铁律

**"通过"的定义 = 用户能完成目标操作，不是"页面没报错"。**

每项测试必须带回证据：API 状态码 + 响应内容 + 截图（含数据）。

---

## 一、测试层级

| 层 | 测什么 | 工具 | 覆盖率要求 |
|------|------|------|------|
| L1 单元 | 组件渲染、工具函数 | Vitest/Jest | 可选，复杂逻辑必测 |
| L2 集成 | API 请求 → 响应对 → 字段映射 | curl / Python script | **每页面必测** |
| L3 E2E | 登录→操作→验证闭环 | Browser + 真实 token | **核心路径必测** |
| L4 异常 | 缺数据、超时、认证失败 | 手动或脚本注入 | 每页面至少 1 条 |

---

## 二、L2 集成测试（核心，每次必跑）

### 原则

**不能只在浏览器里观察 UI**。必须用 token 调 API，验数据返回。

### 每个页面必须验证的检查点

```yaml
认证:
  - POST /auth/register → 201 + token + user_id
  - POST /auth/login → 200 + token
  - GET /auth/me → 200 + {email, role, quota} （带 Authorization header）
  - 无 token → 401
  - 错误密码 → 401
  - OAuth 回调 → 307 重定向

Dashboard:
  - GET /dashboard/stats → 200 + {totalRequests, activeChannels, ...}
  - GET /dashboard/chart/requests → 200 + {records: [...]}
  - GET /dashboard/chart/models → 200 + {labels:[], data:[]}
  - 新用户（无数据）→ 200 + 所有值为 0 或空数组

API Keys:
  - GET /api-keys → 200 + [{id, name, key_prefix, status, created_at}, ...]
  - POST /api-keys {name:"test"} → 200 + {id, key, name, ...} （key 字段非空）
  - DELETE /api-keys/:id → 200
  - 未登录 → 401

Models:
  - GET /models → 200 + 至少 1 个模型
  - 翻页 → 正常分页

Usage:
  - GET /usage → 200 + {records: [...]}
  - 时间范围筛选 → 数据变化

Profile:
  - GET /auth/me → 200 + 完整 profile 数据

Recharge / Payment:
  - GET /api/payment/min-amount?currency_from=usd&currency_to=usdttrc20 → 200 + {min_amount: N}
  - POST /api/payment/create {amount_cents:N,currency:"usd",pay_currency:"usdttrc20"}:
    - 成功 → 200 + {payment_id, pay_address, pay_amount, status}
    - 金额低于最低 → 返回 NOWPayments message 字段
  - GET /api/payment/status/:id → 200 + {status, pay_address, pay_amount}
  - 无 token → 401

Docs:
  - GET /docs → 200
  - 文档内容渲染正常
```

### 关键：字段名验证

**前后端 JSON 字段必须一致。** 常出 bug 的模式：
- `created_at`（后端 snake_case）vs `createdAt`（前端 camelCase）
- `key` vs `fullKey`
- 数字 (`123`) vs 字符串 (`"123"`) — 同一字段不同接口返回不同类型（如 NOWPayments `payment_id`）

**验证方法**：在 L2 测试中打印完整响应 JSON，与前端 TypeScript 接口定义逐字段对比。

## 三、L3 E2E 测试（核心路径）

### 必须覆盖的完整用户流程

```yaml
流程 1: 注册 → 登录 → 仪表盘:
  1. 注册新用户 → 拿到 token
  2. 登录 → 跳转 /dashboard
  3. 仪表盘所有组件渲染（统计卡片 / 图表 / 最近请求表）
  4. 新用户数据为 0（不是 "Failed to load"）
  5. 切换语言（EN → RU → TR）→ 不崩溃，UI 完整

流程 2: API Key 全生命周期:
  1. 创建 API Key → 弹窗显示完整 key（非空白）
  2. 列表中出现新 key，"Created" 列显示日期
  3. 复制 key → 成功
  4. 删除 key → 成功，列表刷新

流程 3: 支付全链路（核心）:
  1. 打开 /recharge → 默认选中 $20
  2. 点击 Pay → 先查 min-amount 校验
  3. 金额低于最低 → 红色提示在金额选择页面显示（不跳转）
  4. 金额足够 → 跳转 QR 码页面
  5. QR 码正常渲染（非空白框）
  6. 支付地址可复制
  7. 状态轮询 GET /api/payment/status/:id → 返回正确状态

流程 4: 使用记录:
  1. 打开 /usage → 表头渲染
  2. 有时间范围筛选
  3. 空数据显示 "No usage data" 而非空白或崩溃

流程 5: 个人中心:
  1. 打开 /profile → 显示用户信息
  2. 角色标签正常渲染
```

## 四、L4 异常边界

每个页面至少验证一条异常路径：

| 页面 | 异常场景 | 期望行为 |
|------|------|------|
| 任意 | token 过期/无效 → 401 | 重定向到 /login |
| Dashboard | 后端超时/挂掉 | 组件框架渲染，显示错误提示（不白屏） |
| API Keys | 创建时网络中断 | 提示错误，不卡在 loading |
| Recharge | 支付创建失败 | 在金额选择页显示错误，不跳转 QR 页 |
| Usage | 数据为空 | 表头渲染，空态提示 |

## 五、多语言验证

每次测试必须切换三种语言：

1. **EN** — 默认，所有 key 必须解析为英文（非 key 名原文）
2. **RU** — 切换到 RU 不崩溃，所有文案显示（允许英文占位）
3. **TR** — 同 RU

**检查方法**：页面加载后在 Console 中执行：
```js
document.querySelectorAll('[class]').length > 0 && !document.body.innerText.includes('apiKeys.')
```
确保没有 i18n key 泄露。

## 七、QA 代理调用规范

当使用子代理跑测试时，prompt 必须包含：

```
必须做的：
1. 用真实 token 调每个页面对应的后端 API，打印状态码和响应 JSON
2. 创建一条数据（API Key / 支付），验证返回字段与前端的 TypeScript 接口一致
3. 切换三种语言（EN/RU/TR），截每个页面的图
4. 每个页面至少验证一条异常路径

禁止做的：
- 只看 UI 渲染就算通过
- 不带 token 调 API
- 不创建数据就说"功能正常"
- 不切换语言
```

## 八、回归检查清单

每次发版前，逐一打勾：

- [ ] 注册新用户 → 登录 → 仪表盘 4 组件渲染
- [ ] 创建 API Key → key 内容显示 → 列表中日期显示
- [ ] 切换 EN/RU/TR，3 页面不崩溃
- [ ] 支付：创建 $20+ → QR 码显示 → status 端点正常
- [ ] API Key 创建 → 用于调用 /v1/chat/completions → 成功
- [ ] 无 token 访问受保护路由 → 重定向 /login
- [ ] Loading 骨架页闪现 → 内容淡入（无白屏闪烁）
- [ ] `npx next build` 零错误
- [ ] `go build ./...` 零错误
