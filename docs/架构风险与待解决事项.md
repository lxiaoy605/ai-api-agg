## 1. OneAPI 升级与源码定制风险

**背景：** OneAPI (`songquanpeng/one-api`, MIT, 29K+ stars) 作为模型代理层，通过 Docker 镜像部署。

**风险：**
- 如果对 OneAPI 源码做二次修改，升级 Docker 镜像时会被覆盖
- OneAPI 更新频率不定，但作为基础设施，安全补丁和 bug 修复需要及时跟上

**策略：**
- **不改 OneAPI 源码**，通过其内置的管理 API（`SYSTEM_ACCESS_TOKEN`）从 Go Backend 调用来配置额度、用户组、渠道
- OneAPI 的 Docker 镜像升级通过蓝绿部署零停机完成：拉新镜像 → 部署到 green → 健康检查 → HAProxy 切换 → 退役 blue

**OneAPI 已有能力（通过 API 可调）：**
- 新用户初始额度配置
- 兑换码系统（批量生成/导出）
- 用户分组 + 分组倍率
- 渠道分组 + 模型映射
- 令牌管理（过期时间、额度、IP 限制）

## 2. 新用户免费福利策略

**约束：** 不能自己掏钱送额度（会被薅羊毛），应利用厂商免费层

**方案：** 多渠道免费层轮询

1. **OneAPI 侧配置"免费渠道组"**：
   - Gemini 免费层 (Google AI Studio free tier)
   - 混元免费层 (腾讯混元 free tier)
   - Groq 免费层 (Groq free tier)
   - DeepSeek 免费额度 (如有)
   - 硅基流动 SiliconCloud 免费额度 (如有)
   - 渠道权重均分，避免单一厂商被打爆

2. **Go Backend 侧配置"付费渠道组"**：
   - 现有付费渠道（DeepSeek、智谱 Z.ai、MiMo 等）

3. **促销逻辑（Go Backend 中间件）**：
   - 新用户注册 → 自动获得促销配额（如每日 100 次免费调用）
   - 免费调用 → 路由到 OneAPI 免费渠道组
   - 促销配额耗尽 → 自动切付费渠道组
   - 可配置促销活动（名称、配额量、有效期、适用渠道组）

4. **实现方式**：
   - Go Backend 负责用户请求的配额检查 + 渠道组选择
   - 通过 HTTP Header 或不同 API endpoint 告知 OneAPI 使用哪个渠道组
   - 不修改 OneAPI 源码，纯配置 + Go Backend 逻辑

## 4. Provider 供应商余额管理

> 2026-06-02 制定

### 问题

供应商余额耗尽 → API 返回 502 → 用户受损 → 管理员后知后觉。

One-API、New-API、LiteLLM 等网关都没有内置 Provider 余额管理功能——转发层不管供应商余额，这是上层业务的事。

### 网关选型分析

| | One-API（当前）| New-API | LiteLLM | One-Hub |
|------|------|------|------|------|
| Stars | 21K | 36.6K | 49K | 2.8K |
| 活跃度 | 维护中 | 非常活跃 | 非常活跃 | 停滞 |
| Failover | ❌ | 加权随机+重试 | ✅ 四层路由 | ❌ |
| DB 兼容 | — | ✅ 完全兼容 | — | ❌ |

**结论：不换网关。** Provider 余额管理独立于网关，Go 后端自建。未来 One-API→New-API 零成本迁移（DB 兼容）。

### 三阶段

| 阶段 | 时间 | 内容 |
|------|------|------|
| 现在 | P0 | Provider 台账 + 内置调度器 + 三级告警 + usage_logs 加 model |
| 近期 | P1 | One-API → New-API（DB 兼容，零迁移）|
| 远期 | P2 | 多供应商冗余，网关前 LiteLLM 或 Go 直连 |

### 告警三级阈值

| 级别 | 条件 | 通知 |
|------|------|------|
| 警告 | < $100 | Telegram |
| 严重 | < $50 | Telegram + Email |
| 危急 | < $10 | Telegram + Email（重复）|

### 已实现

- `provider_balances` 表 + `usage_logs.model` 列
- admin API: GET/POST/PUT/DELETE `/admin/providers`
- 内置调度器: 1min 用户预警 + 30min Provider 扫描 + 6h 管理端预警

## 5. 内置任务调度（替代外部 Cron）

> 2026-06-02

**问题：** 之前用 OpenClaw cron 调用 `localhost:8082` 端点，三个缺陷：
- localhost 只对本机有效，生产 VPS 部署时 OpenClaw 和 Go 后端不在一台机器
- 项目功能割裂到外部系统，部署/迁移/测试复杂度增加
- 不利于将来构建"任务中心"管理界面

**方案：** Go 后端内置 scheduler（`time.Ticker` goroutine，零外部依赖），服务启动时注册所有任务。

**已迁移：** 用户余额预警(1min) + 管理端余额预警(6h) + Provider 余额预警(30min)

**未来任务中心：** 管理 UI 查看任务状态/上次执行/手动触发/暂停/日志持久化
