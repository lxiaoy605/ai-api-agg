## 二、构建规范（四条红线）

### 2.1 红线一：Base Image 永不改 alpine

```yaml
# ✅ 正确
frontend:
  image: node:22

# ❌ 错误
frontend:
  image: node:22-alpine
```

原因：alpine 的 musl libc 与 `@parcel/watcher` 等 npm 包不兼容，且 `node:22` 标准版仅 ~350MB，对 VPS 无压力。

### 2.2 红线二：`next.config.js` 不加 `output: "standalone"`

```js
// ✅ 正确 —— 使用 next start
const nextConfig = {};
module.exports = withNextIntl(nextConfig);

// ❌ 错误 —— 不要加 output: "standalone"
const nextConfig = { output: "standalone" };
```

原因：standalone 模式下 `.next/standalone/.next/static/` 不会自动生成，导致全部 CSS/JS 404。Docker compose 直接用 `npx next start` 即可运行。

### 2.3 红线三：端口永不自动跳变

```bash
# ✅ dev/start 脚本已固定 PORT=3000
npm run dev       # PORT=3000 next dev
npm run start     # PORT=3000 next start
npm run dev:alt   # PORT=3005 next dev（Docker 占 3000 时备用）
```

**为什么：** Next.js 默认行为是 3000 被占就自动选 3001→3002→...，导致端口"乱跳"。现在 `package.json` 中所有脚本都显式设 PORT，不再依赖 Next.js 自动选择。

### 2.5 红线五：Compose 中 HOSTNAME 和 ports 必须正确

```yaml
# ✅ 正确
environment:
  - HOSTNAME=0.0.0.0       # 绑定所有网卡
ports:
  - "3000:3000"            # 主机端口 -> 容器端口

# ❌ 错误 —— 缺一不可
environment:
  # 没有 HOSTNAME=0.0.0.0  ⇒ 外网不可达
ports:
  # 写成 expose: 3000     ⇒ 外部端口不暴露
```

### 2.6 红线六：构建后必须验证

```bash
# 完整验证四步（每个前端部署后必做）
sleep 12                                      # 1. 等容器 ready
docker ps --filter name=ai-api-agg-frontend | grep healthy    # 2. healthy ✓
docker port ai-api-agg-frontend | grep 3000                   # 3. 端口映射 ✓
docker logs ai-api-agg-frontend --tail 3 | grep 'Ready in'    # 4. 启动成功 ✓
curl -s -o /dev/null -w '%{http_code}' http://localhost:3000  # 5. HTTP 200 ✓
```

**< 5 分钟验证 >** — 改完不验证=白改。

### 2.7 根因总结

> **所有错误只有一个根因：改前不查、改后不验。**

## 四、代码风格

### 4.1 Go 后端

| 规则 | 标准 |
|------|------|
| 格式化 | `gofumpt`（比 `gofmt` 更严格） |
| 导入排序 | 标准库 → 第三方 → 内部包，每组空行分隔 |
| 命名 | `CamelCase` 导出，`camelCase` 包内 |
| 错误处理 | 不吞 error，返回结构化 JSON `{ "error": { "code", "message" } }` |
| 配置 | YAML 文件 + 环境变量覆盖（`os.Getenv` > 默认值） |
| 日志 | `slog`（Go 1.21+ 标准结构化日志） |
| 路由 | Gin `r.GET/POST/PUT/DELETE`，中间件链式注册 |

**目录约定：**
```
internal/
├── config/    # 配置加载
├── database/  # DB 连接 & 迁移
├── models/    # 数据模型 + struct
├── middleware/ # 中间件（各一个文件）
├── apikey/    # API Key 模块
├── payment/   # 支付模块
├── audit/     # 审计日志
├── admin/     # 管理 API
└── notify/    # 通知
```

### 4.2 TypeScript / Next.js 前端

| 规则 | 标准 |
|------|------|
| 格式化 | Prettier（单引号，尾逗号，120 字符宽度） |
| 导入排序 | `@/` 内部路径使用绝对引用 |
| React 组件 | 函数组件 + Hooks，禁止 class component |
| 状态管理 | Server State: React Query / Client State: Zustand |
| 样式 | Tailwind CSS classes 优先，禁止内联 style |
| i18n | `next-intl`，消息文件在 `src/messages/{locale}.json` |
| 类型 | 所有 props 显式定义 interface，不 `any` |

**目录约定：**

## 五、前后端字段命名约定

### 5.1 规则矩阵

| 场景 | 标准 | 示例 |
|------|------|------|
| Go 结构体字段（导出） | PascalCase | `AccessToken`, `TotalUsage` |
| Go 结构体 JSON tag | **snake_case** | `json:"access_token"`, `json:"total_usage"` |
| TypeScript 接口 | PascalCase | `interface ApiKeyResponse` |
| TypeScript 字段 | **camelCase** | `accessToken`, `totalUsage` |
| JSON 传输（wire format） | **snake_case** | `access_token`, `total_usage` |
| SQL 列名 | snake_case | `user_id`, `tokens_in` |
| API 路径 | kebab-case | `/api/v1/chat/completions` |

### 5.2 转换约定

Go Backend 输出 JSON 时用 `json:"snake_case"` tag 确保 wire format 为 snake_case。

前端收到 JSON 后，通过类型转换层（DTO）映射为 camelCase：

```typescript
// ❌ 不推荐：前端直接用 snake_case
const balance = data.user_balance;

// ✅ 推荐：定义接口时明确 wire 格式，使用时用 camelCase
interface ApiKeyResponse {
  id: number;
  user_id: string;      // snake_case: wire format
  key_name: string;
}

// 在 lib/api.ts 中做转换
function transformApiKey(raw: ApiKeyResponse) {
  return {
    id: raw.id,
    userId: raw.user_id,        // camelCase: frontend usage
    keyName: raw.key_name,
  };
}
```

> **核心原则：** JSON 传输用 snake_case（与 SQL 一致），前端使用用 camelCase（与 JS 习惯一致）。单文件 DTO 层处理转换，不踩两边。

## 六、Git 工作流

### 6.1 分支策略

```
main ← 生产部署分支
  ├── develop ← 开发主线
  │   ├── feat/xxx    ← 功能分支
  │   ├── fix/xxx     ← 修复分支
  │   └── refactor/xxx ← 重构分支
  └── hotfix/xxx    ← 紧急修复（直接从 main 开）
```

### 6.2 Commit 规范

```
<type>(<scope>): <description>

feat(backend): 添加 NOWPayments 回调处理
fix(frontend): 修复仪表盘日期选择器时区错误
docs: 更新支付流程文档
chore(stack): 升级 OneAPI 镜像版本
refactor(apikey): 重构 Key 加密存储逻辑
```

### 6.3 PR 流程（正式上线后执行）

1. 从 `develop` 开分支 → 开发完成 → PR 到 `develop`
2. CI 检查：lint + build + test
3. Code review 通过 → squash merge 到 `develop`
4. 测试环境验证 → PR 到 `main` → 蓝绿部署上线

### 6.4 单人开发简化

当前团队 1 人，可简化：

```bash
# 直接 main 开发 + 功能分支
git checkout main
git checkout -b feat/xxx
# ... 开发 ...
git commit -m "feat: xxx"
git checkout main
git merge feat/xxx
```

## 九、常见踩坑与教训

### 9.1 构建部署 🔴

| 问题 | 症状 | 根因 | 解决方案 | 严重 |
|------|------|------|---------|:----:|
| alpine 导致 musl 兼容问题 | `@parcel/watcher` 报错，页面崩溃 | alpine 用 musl 替代 glibc | 永不使用 `node:22-alpine` | 🔴 |
| standalone 导致 CSS/JS 404 | HTML 加载成功但白屏 | standalone 模式不自动拷贝 static 目录 | 不用 `output: "standalone"`，用 `npx next start` | 🔴 |
| 缺少 `HOSTNAME=0.0.0.0` | 外网无法访问，健康检查失败 | Next.js 默认绑定容器 hostname 非 0.0.0.0 | 环境变量加 `HOSTNAME=0.0.0.0` | 🔴 |
| 端口 `expose` 而非 `ports` | 容器间可访问但外部不可达 | 误用 `expose`（仅声明端口） | 用 `ports: "3000:3000"` | 🔴 |
| 构建后不验证静态资源 | HTML 引用新 hash 但 static 目录是旧文件 | 构建产物未同步到容器 | 部署后执行四步验证（见红线四） | 🔴 |
| `compose/` 和 `stack/` 混用 | 容器归属不同项目组 | 两个目录都有 compose 文件 | 统一用 `stack/docker-compose.yml` | 🟡 |
| 并发操作 session 锁冲突 | 子 agent 构建失败 | 多终端同时执行 | 一次一个终端，其他等待 | 🟡 |
| 删游离容器后不检查端口映射 | 改完不验证 | 忘记检查 | 四步验证强制执行 | 🟡 |
| 镜像 tag 错误 | 拉取不到镜像或版本不对 | 拼写/版本号错误 | `docker pull` 先验证 tag 存在 | 🟡 |

### 9.2 运行时 🟡

| 问题 | 症状 | 解决方案 |
|------|------|---------|
| SQLite 多容器写冲突 | WAL 模式未启用，蓝绿实例争用 | 确保 `PRAGMA journal_mode=WAL` |
| Next.js 内存不足 | VPS 4GB 内存编译时 OOM | 宿主机构建后部署，不在容器内构建 |
| 容器时区错误 | 日志时间 UTC，无亚美尼亚时间 | 加 `TZ=Asia/Yerevan` 环境变量 |
| docker compose 网络问题 | 服务间 hostname 无法解析 | 确保同一 docker network，用服务名通信 |

### 9.3 前端 🟡

| 问题 | 症状 | 解决方案 |
|------|------|---------|
| CSS 变量在 canvas 中无效 | Recharts 图表颜色不对 | chart 颜色用 JS 传值而非 CSS 变量引用 |
| 动态 import 导致 SSR 失败 | 页面白屏 | `next/dynamic` + `{ ssr: false }` 包裹客户端组件 |
| `next-intl` 路由匹配失败 | 页面 404 | `next.config.js` 中正确配置 `i18n` 或 plugin |

### 9.4 Docker Compose 🟡

| 错误 | 根因 | 检查 |
|------|------|------|
| `docker: 'compose' is not a docker command` | 旧版 Docker 用 `docker-compose`（带横线） | 新版用 `docker compose`（无横线） |
| `no configuration file provided` | 没指定 -f | 确认 `cd stack/` 或 `-f stack/docker-compose.yml` |
| `container name already in use` | 上次未清理 | `docker compose down` 或 `docker rm -f` |
